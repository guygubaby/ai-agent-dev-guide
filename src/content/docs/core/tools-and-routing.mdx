Agent 工具是模型与业务代码之间的稳定协议。好的工具名表达用户意图，schema 足够窄，结果有机器可读的成功/失败语义。

## 工具设计原则

### 读写分离

读取工具无副作用，可以更积极地开放；写入工具必须通过 Action 层并经过权限、目标、参数和版本验证。

### 一个工具表达一个领域动作

推荐：

- `update_node_styles({ nodeId, viewport, styles })`
- `update_node_properties({ nodeId, changes })`
- `update_node_dynamic_binding({ nodeId, field, binding })`

不推荐：

```ts
apply_patch({ path: 'page.children[4].data.html', value: '<h1>...</h1>' })
```

任意 path 工具很难做权限、类型、业务不变量和审计；模型也容易因为数组顺序变化而修改错误节点。

### 输入和输出都要结构化

```ts
const UpdateStylesInput = z.object({
  nodeId: z.string().uuid(),
  viewport: z.enum(['PC', 'MOBILE']),
  styles: z.record(
    z.enum(['display', 'gap', 'color', 'fontSize', 'textAlign']),
    z.string().min(1).max(80),
  ),
})

type ToolResult =
  | { ok: true; nodeId: string; changed: string[]; undoId: string }
  | { ok: false; code: 'NOT_FOUND' | 'FORBIDDEN' | 'STALE_CONTEXT' | 'INVALID_VALUE'; message: string }
```

模型看到 `ok: false` 后应该修正参数或向用户解释，而不是声称操作完成。

## Zod 只解决第一层校验

Zod 会拒绝形态错误的 tool call，但业务 Action 仍需验证：

- 当前用户是否有写权限。
- 页面是否处于可编辑状态。
- nodeId 是否仍属于当前页面。
- 当前设计端是否与请求一致。
- CSS value、HTML、URL 或动态数据 ID 是否在业务允许范围。
- 乐观版本是否仍然匹配。

Tool call 是不可信输入，不是授权凭证。

## 渐进式工具路由

复杂编辑器很容易增长到二十多个工具。如果每一步都发送全部 schema，会增加 prompt token，并提高模型在相似工具之间误选的概率。

推荐把工具分为：

```ts
const groups = {
  discovery: [
    'get_page_context',
    'get_selected_node_context',
    'get_pages',
    'get_site_settings',
    'get_site_menus',
  ],
  canvasWrite: [
    'create_component',
    'update_node_styles',
    'update_node_properties',
    'delete_component',
  ],
  pageWrite: ['create_page', 'update_page_settings', 'delete_page'],
  siteWrite: ['create_site_settings', 'update_site_settings', 'delete_site_settings'],
  menuWrite: ['create_site_menu', 'update_site_menu', 'delete_site_menu'],
}
```

路由状态机：

<Steps>
1. 第一步只开放 discovery tools。
2. 调用画布读取工具后，解锁画布写入；调用页面读取后，解锁页面写入。
3. 页面创建或打开成功后，可以解锁画布工具继续编辑新页面。
4. 删除工具只有在存在匹配且未过期的确认状态时才开放或执行。
5. 超过步骤上限、用户停止、页面 scope 改变时结束循环。
</Steps>

```ts
function getActiveTools(steps: AgentStep[], latestText: string) {
  const called = new Set(steps.flatMap(readToolNames))
  const active = new Set(groups.discovery)

  if (called.has('get_page_context') || called.has('get_selected_node_context')) {
    groups.canvasWrite.forEach(name => active.add(name))
  }
  if (called.has('get_pages')) {
    groups.pageWrite.forEach(name => active.add(name))
  }
  if (called.has('get_site_settings')) {
    groups.siteWrite.forEach(name => active.add(name))
  }
  if (called.has('get_site_menus')) {
    groups.menuWrite.forEach(name => active.add(name))
  }
  return [...active]
}
```

## Tool description 怎么写

工具描述要让模型知道：

1. 何时使用，何时不要使用。
2. 是否必须先调用某个读取工具。
3. 目标字段和单位语义。
4. 成功/失败结果如何解释。
5. 是否危险、是否需要确认。

描述不是替代代码校验。像“不要删除重要页面”这样的自然语言无法构成权限边界。

## 失败语义

为所有工具统一返回错误码，比抛出不透明异常更利于模型自我修复和 UI 呈现：

| code | 下一步 |
| --- | --- |
| `NOT_FOUND` | 重新读取 Context，不使用旧 ID |
| `STALE_CONTEXT` | 告知状态已变化，重新读取后再决定 |
| `FORBIDDEN` | 停止尝试，向用户解释权限限制 |
| `INVALID_VALUE` | 根据字段规则修正参数 |
| `CONFIRMATION_REQUIRED` | 渲染确认卡片，等待用户 |
| `CONFLICT` | 重新获取资源版本或让用户选择 |

<Aside type="caution" title="不要自动无限重试">
重试只适合瞬时网络故障和幂等读取。写操作在不知道服务端是否已成功时不得盲目重复；必须依赖 idempotency key、资源版本或读后确认。
</Aside>

## 批量与粒度

一次用户意图包含多个相邻样式时，可以让一个 `update_node_styles` 原子地写入多个受限字段；不要拆成十次布局抖动。跨资源修改则应使用明确的复合事务，或逐项执行并报告部分失败，不能让模型假装全部成功。
