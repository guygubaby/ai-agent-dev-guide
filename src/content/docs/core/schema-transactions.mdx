页面编辑器的 AI 工具最终会修改 Store 中的 JSON Schema，但“最终修改 JSON”不意味着应该开放任意 JSON patch。模型只表达意图；业务层负责把意图转换成符合组件模型的事务。

## 事务边界

一次 Agent 写操作应遵循：

<Steps>
1. 捕获当前 `pageId`、Schema version、viewport 与 selected UUID。
2. 按稳定 ID 从当前 Store 重新找到目标节点。
3. 验证权限、节点类型、字段白名单和值约束。
4. 生成快照或 inverse patch。
5. 在一个事务内修改 Schema，并执行必需的派生计算。
6. 刷新 memo/画布，等待 DOM 重绘。
7. 在原 PC/Mobile 设计端按 UUID 重新绑定选中节点。
8. 标记页面未保存，并返回 `undoId` 与变更摘要。
</Steps>

任何一步失败都不应留下半成品状态。

## 一个最小事务管理器

```ts
interface Snapshot<T> {
  id: string
  pageId: string
  viewport: 'PC' | 'MOBILE'
  selectedNodeId?: string
  before: T
}

async function runSchemaTransaction<T>(
  label: string,
  mutate: () => void,
): Promise<{ undoId: string }> {
  const snapshot = captureSnapshot<T>()

  try {
    mutate()
    await rebuildDerivedStyles()
    await refreshCanvas()
    await restoreSelection(snapshot.selectedNodeId, snapshot.viewport)
    markUnsaved()
    commitUndo(snapshot, label)
    return { undoId: snapshot.id }
  } catch (error) {
    restoreSnapshot(snapshot)
    await refreshCanvas()
    await restoreSelection(snapshot.selectedNodeId, snapshot.viewport)
    throw error
  }
}
```

大型 Schema 可以保存结构化 inverse patch，减少深拷贝成本；但 inverse patch 必须覆盖派生字段，否则撤销后可能视觉状态不一致。初版可以可靠恢复为优先，保存 AI 修改前的 Schema 和选择上下文。

## 创建组件必须经过工厂

组件工厂负责默认字段、UUID、版本和嵌套结构。Agent 不应凭空拼出组件对象：

```ts
const component = componentSchemaMap[input.componentType].create()
applyAllowedProperties(component, input.properties)
```

如果要在页面根部加入一个普通横向内容区块，推荐默认结构：

```text
Frame（全宽背景）
└─ PageSection（内容最大宽度与左右安全间距）
   └─ 用户请求的组件或 Container
```

只有用户明确要求全屏背景/全宽内容时才跳过 `PageSection`。这条规则把内容宽度规范放进结构，而不是依赖模型每次记得设置 `max-width`。

## 样式、内容、配置和行为要分开

| 意图 | 工具 | 示例 |
| --- | --- | --- |
| 布局与视觉 | `update_node_styles` | gap、颜色、字号、对齐 |
| 原子类兜底 | `update_node_custom_classes` | `grid grid-cols-2 gap-5` |
| 静态字段/配置 | `update_node_properties` | 文案、alt、href、组件选项 |
| 重复列表 | `update_node_list_data` | Carousel slides |
| 动态数据 | `update_node_dynamic_binding` | 绑定数据源及字段映射 |
| 结构 | `create_component` / `delete_component` | 插入、移动、删除 |

这种分离让每个工具拥有更窄的字段白名单与更清晰的审计记录。

## Custom Class 与预生成样式

如果编辑器的 Custom Class 支持 UnoCSS 原子类，编辑端可以把解析结果保存到 Schema：

- `dynamicStyleObject`
- `mobileDynamicStyleObject`
- `extraDynamicStyleObject` 中的响应式、hover 等规则

渲染端可以消费这些预生成结果，而不是重新运行完整 UnoCSS。因此 AI 修改 Custom Class 时必须等待编辑端转换完成，并在同一事务中写入派生样式字段后再返回成功。否则可能出现 DOM 有 class，但发布页面无 CSS。

Custom Class 应是样式面板无法表达时的兜底，而不是所有布局修改的首选。类名必须经过允许字符检查，并由实际 UnoCSS generator 验证能生成规则。

## HTML 写入

富文本字段可以接受安全 HTML，但必须使用独立业务白名单：

- 允许排版标签：`p`、`br`、`strong`、`em`、标题、列表、`a` 等。
- 链接只允许 `http`、`https`、`mailto`、`tel` 等协议。
- 禁止脚本、表单、iframe、事件属性、`javascript:`、`url()`。
- inline style 只开放文字排版属性，不开放定位、背景 URL 和行为相关 CSS。

聊天 Markdown 的 DOMPurify 策略不能直接替代持久化富文本策略；两者威胁面不同。

## 删除与撤销

可撤销不代表可以取消确认。删除页面、菜单、站点配置等高风险操作仍需二次确认；画布组件删除即使有 Undo，也应在删除范围较大或包含子树时明确展示影响。

<Aside type="tip" title="保持选择的关键">
不要保存 Moveable 或 DOM Element 引用。重绘后它们已经脱离 DOM。只保存 UUID 与 viewport，等待下一帧或画布刷新完成后重新 query 并绑定。
</Aside>
